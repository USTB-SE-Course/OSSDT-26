## 1. 项目用途与选择原因

uv 是 Astral 团队开发的一个 Python 包与项目管理器，用 Rust 写成，定位是把过去分散在 pip、virtualenv、pip-tools、pipx 等工具里的工作合并到同一个命令行程序里：创建和激活虚拟环境、解析依赖、生成并锁定依赖版本、安装包，以及下载和管理 Python 解释器版本，都能用它一条命令完成。它面向的主要用户是需要同时维护多个 Python 项目的开发者，以及在 CI 中反复从零安装依赖、要求安装过程可复现的团队。uv 读取 `pyproject.toml`，也兼容传统的 `requirements.txt`，并把解析结果写进跨平台的 `uv.lock`，从根本上解决“我这能跑、你那里装不上”的依赖漂移问题。官方文档把速度和统一工具链作为两个核心卖点。

选择它有三个原因。第一，它与本课程直接相关：第 3 讲讲项目依赖管理，作业 3 要求用 uv 管理环境和依赖，调研 uv 能让我先弄清依赖声明、锁文件、可复现环境这几个概念在真实项目里是怎么落地的。第二，我自己在做 Python 练习时用过 `uv add` 和 `uv sync`，对它的行为有直观感受，读文档时能判断描述是否与实际一致，而不是只看宣传。第三，这个仓库公开、许可证明确、维护记录密集，很容易找到可核查的证据来支撑判断。

## 2. 开源许可证

仓库根目录下同时存在两份许可证文件：[LICENSE-MIT](https://github.com/astral-sh/uv/blob/main/LICENSE-MIT) 和 [LICENSE-APACHE](https://github.com/astral-sh/uv/blob/main/LICENSE-APACHE)，而 `Cargo.toml` 里声明的许可证字段是 `license = "MIT OR Apache-2.0"`。这说明 uv 采用的是双许可：使用者可以在 MIT 和 Apache-2.0 之间任选其一。

以 Apache-2.0 为例，再分发时需要注意的义务是：必须随作品保留版权声明和许可证文本；如果原作品带有 NOTICE 文件，再分发时要一并保留其中的内容；对被修改过的文件，需要加上显著的“已修改”说明，不能让人误以为改动出自原作者。也就是说，uv 可以被自由使用、修改和商用，但署名与许可声明这条线不能省。
