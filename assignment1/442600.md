## 1. 项目用途与选择原因

我这次调研的项目是 uv，它是 Astral 公司开发的 Python 包管理与项目管理工具，核心用 Rust 编写。

它要解决的问题，是 Python 开发里的工具过于松散的问题。安装依赖用 pip，锁定版本用 pip-tools，建虚拟环境用 virtualenv 或 venv，临时跑命令行工具需要 pipx，每个环节各有各的配置。uv 把这些收拢进一个可执行文件：安装和解析依赖、创建虚拟环境、生成并校验 `uv.lock`、管理 Python 解释器版本，还能用 `uvx` 临时运行工具。因为底层是 Rust，再加上全局缓存和并行下载，它在装包和解析依赖这两步上比基于 Python 的同类工具快很多。

它的目标用户我大致归成三类：一是日常写 Python 应用或库的开发者，想用一套命令把环境和依赖管好；二是在 CI/CD 里要压缩构建时间的团队，快速安装依赖实现收益；三是需要环境可复现的数据科学和科研用户，锁文件对他们尤其重要。另外 Astral 还维护代码检查工具 ruff，两个项目的思路一致，都是用 Rust 重写 Python 的基础设施。

选它主要有两个原因。一是课程第三讲讲依赖管理，用的实践工具就是 uv，我对它的基本命令和概念有一定了解；二是它 2023 年 10 月才建仓库，短短三年就有了相当大的社区规模，是观察一个新项目怎么快速做出生态的好样本。

## 2. 开源许可证

uv 是 **MIT 和 Apache-2.0 双许可**，用的人可以任选一个遵守。仓库根目录下两个许可证文件都在：[LICENSE-MIT](https://github.com/astral-sh/uv/blob/main/LICENSE-MIT) 和 [LICENSE-APACHE](https://github.com/astral-sh/uv/blob/main/LICENSE-APACHE)，README 的 License 段落也写明了 licensed under "either of"。

这里要提醒一点：GitHub 页面右侧边栏只显示 `Apache-2.0`，容易误导人们以为只有一种许可。实际这是平台对双许可项目的显示方式，真正的范围要看仓库里那两个文件。

使用时的义务，两个许可证共同的一条是：再分发时必须保留原有的版权声明和许可证文本。如果选了 Apache-2.0 并且修改了源文件，还要在修改过的文件里注明做过变更。对想把 uv 打进内部工具链、或者做二次分发的团队来说，这一条不能忽略。

## 3. 维护与活跃情况

我从两个方面观察。

一是发布节奏。根据 [Releases 页面](https://github.com/astral-sh/uv/releases)，2026 年 10 月 27 日到 11 月 24 日这一个月里发了 5 个版本：0.13.6（10 月 27 日）、0.13.7（11 月 3 日）、0.13.8（11 月 12 日）、0.13.9（11 月 17 日）、0.13.10（11 月 24 日），基本一周一个。采用高频的小版本迭代，说明维护者是在持续往外交付修复和功能，进行实时更新。

二是提交活动。[main 分支](https://github.com/astral-sh/uv/commits/main) 最近 5 次提交都集中在 11 月 24 日到 26 日，内容涉及 Docker 镜像更新、Python 版本同步、依赖版本校验和发版提交，PR 编号已经排到 #23407。合并接近每天都在发生，改动也不局限在某一个模块。

两点合起来，我的判断是 uv 目前维护得相当活跃，背后有公司团队在持续投入。

不过证据也有局限：仓库现在有 3104 个未关闭的 issue 和 PR，贡献者 613 人（这个口径把匿名提交也算进去了，属于上限值）。这说明项目在快速扩张的同时，待办也积了不少。另外我只看了最近一个月，没法据此判断更长时间线上的稳定性。所以目前只能确认项目活跃，是否长期稳定还需要观察。
