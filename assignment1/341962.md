## 1. 项目用途与选择原因

**主要用途**：FastAPI 是一个用于编写 Web API 的 Python 后端框架。开发者用 Python 类型注解声明请求参数和数据模型，框架据此自动完成数据校验与序列化，并按照 OpenAPI 标准自动生成可交互的接口文档（Swagger UI）。它的 Web 部分基于 Starlette，数据部分基于 Pydantic（见 [README](https://github.com/fastapi/fastapi#readme)）。

**目标用户**：需要快速搭建 REST API 的 Python 后端开发者，以及需要把机器学习模型封装成在线服务的算法工程师。README 引用了 Microsoft、Uber、Netflix 等团队的使用评价，例如 Netflix 开源的危机管理编排框架 Dispatch 就是基于 FastAPI 构建的。

**选择原因**：我此前没有实际使用过 FastAPI，选择它主要有两点考虑：一是本课程以 Python 开源开发为主线，FastAPI 是 Python 生态中常用的 Web 框架，后续做课程项目时可能会用到；二是它的仓库本身就使用了课程后面要学的 uv（`uv.lock`）、pre-commit 和 GitHub Actions，可以作为工程规范的参照样本。

### 3.3 Issue、讨论区与参与方式

FastAPI 的参与方式和多数项目不同：

1. **Issue 只能由维护者创建。** 仓库[禁用了空白 Issue](https://github.com/fastapi/fastapi/blob/master/.github/ISSUE_TEMPLATE/config.yml)，唯一的 Issue 模板要求勾选“我是 @tiangolo 或他直接要求我创建”。因此整个仓库只有 1 个开放 Issue，即 2023 年创建的 [Roadmap #10370](https://github.com/fastapi/fastapi/issues/10370)。提问、反馈 Bug 和功能建议都应发到 [GitHub Discussions](https://github.com/fastapi/fastapi/discussions/categories/questions)，安全漏洞则发邮件到 security@tiangolo.com。
2. **先讨论，再提 PR。** [贡献指南](https://tiangolo.com/open-source/contributing/)要求先开 Discussion，团队成员明确要求后才能提交 PR，[PR 模板](https://github.com/fastapi/.github/blob/main/.github/pull_request_template.md)中也写了这一点。最近被关闭的外部 PR 印证了这条规则：[#16745](https://github.com/fastapi/fastapi/pull/16745)（2026-11-14）、[#16777](https://github.com/fastapi/fastapi/pull/16777)（2026-11-16）、[#16789](https://github.com/fastapi/fastapi/pull/16789)（2026-11-20）都因为没有先讨论而被维护者关闭。三个 PR 都在创建当天就收到了回复，维护者解释了规则。
3. **开发规范。** 用 `uv sync` 安装依赖，用 `prek`（pre-commit 钩子工具）在提交前做格式化和检查，用 `pytest` 运行测试。外部贡献者**不允许修改** `pyproject.toml` 和 `uv.lock`，以防范供应链风险。
4. **AI 使用政策。** 允许使用 AI 工具，但要求有实质性的人工投入。看起来是 AI 批量生成的 PR 和评论会被关闭，反复发送这类内容的账号会被封禁。

除了提交代码，还可以在 Discussions 的 Questions 分类中提问和交流，在 Translations 分类中协调文档翻译，或在 Show and tell 分类中展示基于 FastAPI 的作品。

### 3.4 综合判断与局限

**判断**：FastAPI 处于积极维护状态，版本发布频繁，维护者对新 PR 的响应很快。但开发高度依赖 @tiangolo 一个人，存在一定的“巴士因子”风险；对外部贡献的门槛也比较高，新人更适合从 Discussions 开始参与，而不是直接提 PR。

**局限**：（1）数据是 2026-11-22 的快照，只覆盖最近大约一个月；（2）机器人提交会拉高 Commit 和 PR 数量，我已经尽量把它们区分出来；（3）用户问题主要在 Discussions 中讨论，我没有统计那里的回复率，所以无法量化评价项目对用户提问的响应速度。
